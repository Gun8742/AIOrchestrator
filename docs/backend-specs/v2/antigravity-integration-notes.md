# Antigravity CLI integration: ผลตรวจเบื้องต้น

## สถานะล่าสุด — 2026-10-30: OAuth integration ใช้งานจริง

- ผู้ใช้ยืนยัน Login และรัน container ใหม่ผ่านทั้งสองรอบแล้ว จากนั้น `TestOAuthContainerTurn` ผ่านกับ runtime ของ Backend จริง: ตรวจ init permission/cwd/model ก่อนส่ง prompt, ได้ `PIXEL_OAUTH_BACKEND_OK` และยืนยัน container หยุดหลัง cancel ระหว่างเริ่มทำงาน ไม่ได้ใช้ tool ของ model ในการทดสอบ cancellation รอบนี้
- `TestWorkflowHTTPMixedOAuthHandoff` ผ่าน HTTP → PostgreSQL → worker → Codex → Antigravity OAuth จริง ผลลัพธ์สังเคราะห์ส่งต่อกันตาม step ไม่มี API key และตั้งเครดิตเพิ่มปิดอยู่
- Production ลงทะเบียน Antigravity เมื่อ `LoadOAuthRuntime` ตรวจ Docker daemon, image digest/entrypoint/auth label และ OAuth volume label ได้ครบ Availability หมายถึง runtime ติดตั้งพร้อม ส่วน account access ตรวจเมื่อเริ่ม execution และยัง fail ได้เมื่อ session หมดอายุหรือโควตาหมด
- `CreateOAuthContainer` mount เฉพาะ project กับ OAuth volume ที่ตรวจ ownership label แล้ว และตรวจ mounts ก่อนเริ่ม; fixture path ไม่ mount session ของผู้ใช้ Entry script ตัด API-key/ADC environment และเขียน settings `useG1Credits:false` แบบ atomic
- Worker ลบเฉพาะ container ที่ยืนยันหยุดแล้วหลัง terminal transaction สำเร็จ; หาก DB commit ไม่สำเร็จหรือ execution ไม่ยืนยัน ต้องเก็บ container ไว้เพื่อ recovery การลบใช้ `docker rm` โดยไม่มี force และไม่ลบ OAuth volume Cleanup error ไม่เปลี่ยนผลที่ commit แล้วและแจ้ง generic log เพื่อดำเนินการต่อ
- Backend suite ผ่านพร้อม `-race`, PostgreSQL และ `DOCKER_CONTAINMENT_TEST=1` รวม ownership, FIFO, recovery, container cleanup และการปฏิเสธลบ container ที่ running
- เก็บขั้นตอน Login ที่รันซ้ำได้ใน `scripts/login-agy.sh`; บันทึกด้านล่างเป็นประวัติช่วงที่ยังไม่เปิด provider ไม่ใช่สถานะปัจจุบัน

## สถานะล่าสุด — 2026-10-30: Google AI Pro OAuth

ผู้ใช้มี Google AI Pro และต้องการใช้โควตาเดิมโดยไม่เปิด API billing จึงเปลี่ยนจาก API key มาเป็น Google Account OAuth บันทึกเกี่ยวกับ API-key setup ด้านล่างเป็นประวัติก่อนเปลี่ยนแนวทาง

- Image entrypoint ตัด API-key/ADC environment ที่เกี่ยวข้อง และเขียน settings ของแอปเป็น `{"useG1Credits":false}` ทุกครั้ง ไม่มี `modelProvider: gemini`; `CreateContainer` ไม่ส่ง `GEMINI_API_KEY` เข้า Docker และ launcher ไม่อ่าน key จาก `.env` อีกแล้ว ไม่ได้ลบ key หรือเปลี่ยน billing ของบัญชีผู้ใช้
- เตรียม OAuth wizard ชั่วคราว `/tmp/pixel-agy-oauth-setup.sh` ให้ผู้ใช้ Login เองใน Terminal/browser ด้วยบัญชี Personal ที่มี AI Pro: container แบบ non-root/read-only ไม่มี project mount ใช้ Docker volume `pixel-agent-office-agy-auth` แยกเก็บ session และไม่คัดลอก macOS Keychain ไม่ส่ง auth URL/code เข้าแชต
- Wizard ทดสอบ prompt สังเคราะห์แล้วเริ่ม container ใหม่ด้วย volume เดิม และตรวจ `SUCCESS` กับข้อความ `PIXEL_OAUTH_OK` ก่อนรายงานว่าผ่าน ต้องให้ผู้ใช้รันเอง ยังไม่มีหลักฐาน OAuth persistence กับบัญชีจริง และ runtime สำหรับ task ยังไม่ได้ mount auth volume นี้
- ตรวจ syntax ของ entrypoint/wizard และ Python launcher tests ผ่าน; tests ของ runtime จำลองตรวจว่าไม่ส่ง API key และ settings ปิดเครดิตเพิ่ม ส่วน volume test ตรวจเพียง owner permissions กับข้อมูลสังเคราะห์ข้าม container ไม่ใช้ token จริง
- Production ยังเปิดเฉพาะ Codex จนยืนยัน OAuth, model, cancellation และ cleanup กับ integration จริง การตั้ง `useG1Credits:false` อ้างอิง [CLI credits](https://antigravity.google/docs/cli/credits); quotas และ overages อ้างอิง [Plans](https://antigravity.google/docs/plans/)

## สถานะล่าสุด — 2026-10-29 หลังอนุญาต network

- ผู้ใช้อนุญาต Docker bridge เพื่อเชื่อม Gemini ด้วย prompt สังเคราะห์แล้ว; `CreateContainer` และการตรวจ configuration เปลี่ยนจาก `none` เป็น `bridge` ไม่มีการเปิด ports, mount Docker socket หรือคัดลอก credentials ของ host
- Container ทดสอบแบบ read-only/non-root ติดต่อ `https://antigravity.google/docs/cli/install/` ผ่าน HTTPS สำเร็จ ผลนี้ยืนยันเส้นทาง DNS/TLS เท่านั้น ไม่ยืนยัน model authentication
- CLI 1.4.9 ใน HOME ว่างยังแสดงขั้นตอน authentication และไม่คืนผลจาก synthetic prompt ภายใน 20 วินาที จึงหยุดและลบ container ทดสอบ ไม่บันทึก auth payload หรือ URL
- Docker tests สำหรับ create, run/handshake/model mismatch, cancellation ระหว่าง subprocess และ stop ผ่านพร้อม race detector หลังใช้ bridge; runtime ใน run tests เป็น fixture และไม่ได้ส่งคำขอ model จริง
- Production ยังเปิดเฉพาะ Codex ผู้ใช้เลือก Gemini API key และจะตั้ง key เอง รอการตั้ง authentication ใน container แล้วจึงทดสอบ Gemini 3.8 Flash, cancellation และ mixed workflow จริง ข้อความเกี่ยวกับ `--network none` และการรออนุญาตในบันทึกด้านล่างเป็นสถานะก่อนหน้านี้
- เพิ่ม entrypoint ใน image เพื่อสร้าง settings `modelProvider: gemini` ใน HOME tmpfs เมื่อมี API key; `docker create --env GEMINI_API_KEY` รับค่าจาก Backend environment โดยไม่มีค่า key ใน arguments ตัว launcher อ่าน optional key จาก git-ignored `.env` และให้ environment เดิมมีลำดับความสำคัญสูงกว่า
- Key อยู่ใน Docker container configuration เมื่อใช้ environment authentication จึงอ่านได้โดยผู้มีสิทธิ์ Docker daemon จนกว่า container ถูกลบ Smoke test ใหม่เป็น opt-in `AGY_CONTAINER_SMOKE=1` และลบ container หลังจบ; ยังไม่เปิด production executor ซึ่งต้องจัดการ container/credential cleanup หลัง commit terminal state ก่อนเปิดใช้
- การตั้ง key ใช้ wizard ชั่วคราว `/tmp/pixel-gemini-key-setup.sh` ที่ผู้ใช้รันเอง: input ซ่อนข้อความ, บันทึกใน `.env` ด้วย permission 0600 และไม่ตั้งค่า CI หรือส่ง key ผ่านแชต ไม่มีการรัน wizard แทนผู้ใช้
- วิธี authentication ทางการมี Google Account OAuth และ Gemini API key; API key ต้องตั้ง `modelProvider: gemini` ด้วย และไม่ใช่การนำ session บน host มาใช้โดยอัตโนมัติ ดู [Authenticate](https://antigravity.google/docs/install?tab=cli) และ [Headless mode](https://antigravity.google/docs/cli/headless/)

ตรวจเมื่อ 2026-10-28 โดยใช้ `agy` ที่ติดตั้งบนเครื่องและ prompt สังเคราะห์ใน directory ชั่วคราว ไม่เปิด provider ในเว็บจากผลตรวจนี้

- `--model gemini-3.8-flash-medium`, `--mode plan`, `--sandbox`, `--print` และ `--output-format stream-json` ใช้ร่วมกันได้ในการทดสอบที่ไม่เรียก tool; CLI ส่ง JSON lines ประเภท `init`, `step_update` และ `result` และ final result มี `status`, `response` และ usage
- ผล `init` รายงาน `permission_mode` เป็น `request-review`; การรัน headless ที่ต้องใช้ tool ซึ่งรอ permission ถูกปฏิเสธอัตโนมัติในการทดสอบก่อนหน้า ห้ามตีความว่ามี interactive approval ผ่านเว็บแล้ว
- `--disable-slash-commands` ทำให้ `--mode plan` ไม่มีผลตามคำเตือนจาก CLI จึงห้ามพึ่ง combination นี้เป็นหลักฐานว่ามี read-only mode
- ยังต้องพิสูจน์ authentication และเงื่อนไขการใช้งาน, การส่ง approval จากเว็บ, การหยุด task และ subprocess, error/timeout, event schema รวมถึงการแยกความลับก่อน persist และ FIFO ร่วมกับ Codex ตาม [Multi-provider spec](01-multi-provider.md) ก่อนเปิด provider
- Event ที่สังเกตเป็นผลของ CLI เวอร์ชันที่ติดตั้ง ไม่ใช่สัญญาว่า schema จะคงที่ การ implement ต้องตรวจ version และ fail closed หากไม่รู้จัก event ที่สำคัญต่อ lifecycle
- ทดสอบส่ง SIGINT ไปยัง process group แยกหลังได้รับ `init` จาก prompt สังเคราะห์ที่ห้ามใช้ tools: CLI ออกด้วย exit status 1 ภายใน 15 วินาที และ process group เดิมไม่เหลืออยู่ในการตรวจครั้งนั้น ผลนี้ยังไม่พิสูจน์ cancellation ระหว่าง tool ทำงาน, subprocess ที่แยก process group หรือสถานะของงานฝั่ง provider
- Changelog ของ CLI ระบุว่า `--input-format stream-json` รับข้อความ prompt แต่ละ turn ผ่าน stdin; ไม่ได้ยืนยัน contract สำหรับตอบ permission ผ่าน stream ดังกล่าว และ headless จะ soft-deny เมื่อ tool ต้องรอการยืนยัน
- Changelog ระบุว่า permission denial หรือ tool error บางชนิดไม่ทำให้ exit code เป็น non-zero จึงห้ามใช้ exit code หรือ `result.status` เพียงอย่างเดียวเพื่ออ้างว่า Agent ทำทุกขั้นตอนสำเร็จ; ต้องตรวจ event และผลลัพธ์จริงก่อนกำหนด lifecycle
- [เอกสาร Headless ของ Antigravity](https://antigravity.google/docs/cli/headless/) ยืนยันว่าโหมดนี้ไม่มี interactive permission prompt: คำขอที่ต้องถามและไม่ได้รับอนุญาตจะถูก soft-deny แต่ process อาจ exit 0; โดยปริยายการอ่าน/เขียนใน workspace อาจได้รับอนุญาต ส่วน command ที่ต้องถามถูกปฏิเสธ ดังนั้น UI ต้องสื่อขอบเขตจริงก่อนส่งงาน และห้ามตีความ exit 0 ว่าไม่มี permission denial
- เอกสารเดียวกันระบุชนิด event `init`, `step_update`, `result`; หากจะใช้ headless integration ต้องจัดการ stderr สำหรับ permission notice อย่างปลอดภัย ไม่ persist prompt, credential หรือ raw stderr โดยปริยาย และรายงาน interactive approval ว่าไม่รองรับจนกว่าจะมี interface ที่ตรวจสอบได้
- Smoke test ด้วย `pwd` ใน directory ชั่วคราวพบ `step_update` ของ `run_command` ที่ `state: ERROR`, stderr แจ้ง headless permission denial และ terminal `result` ระบุ `status: SUCCESS` พร้อม `denied_actions` และ response ว่าง; process exit 0 จึงยืนยันว่า adapter ต้องตรวจ denial แยกจาก status และ exit code
- ทดสอบส่ง prompt สังเคราะห์ผ่าน stdin ด้วย `--input-format stream-json --output-format stream-json` แล้ว ได้ `init`, `step_update` และ `result` ตาม [เอกสารทางการ](https://antigravity.google/docs/cli/headless/) จึงสามารถออกแบบ adapter โดยไม่ใส่ prompt เป็น command-line argument; ยังไม่ได้พิสูจน์การยกเลิกขณะ tool มี subprocess
- ทดสอบขอให้สร้างไฟล์สังเคราะห์ใน workspace ชั่วคราวด้วย permission ปกติ พบว่า `write_file` ถูก soft-deny และ terminal result มี `denied_actions` แม้ status เป็น `SUCCESS`; พฤติกรรมนี้ขึ้นกับ policy ที่ effective ใน environment จึงห้ามสมมติว่าการเขียน workspace จะได้รับอนุญาตเสมอ
- ผู้ใช้อนุญาตให้ทดสอบ `sleep 37` ด้วย allow rule ชั่วคราว: stream รายงาน `run_command` เป็น `ACTIVE` และ CLI ออกหลังส่ง SIGKILL ให้ process group; rule ถูกลบและตรวจซ้ำแล้ว การตรวจ process group หลังจบถูกระบบปฏิเสธ (`EPERM`) และ event `ACTIVE` เพียงอย่างเดียวไม่ยืนยันว่า subprocess เริ่มหรือหยุดจริง จึงยังไม่ใช่หลักฐานเพียงพอสำหรับปล่อยคิว
- Adapter ปฏิเสธ step ที่ไม่มีชนิดหรือสถานะที่รู้จัก และถือว่า tool ล้มเหลวเมื่อมี `tool_info.error` แม้ state เป็น `DONE` หรือผลรวมเป็น `SUCCESS`; รายการชนิด step อิงตัวอย่างที่ตรวจพบ จึงต้องตรวจ CLI รุ่นใหม่ก่อนเพิ่มชนิดอื่น ([Headless mode](https://antigravity.google/docs/cli/headless/))
- ทดสอบซ้ำด้วยคำสั่ง `sleep 37` ที่ผู้ใช้อนุญาต โดยตรวจ process list ก่อนและระหว่างรัน: พบ sleep process ใหม่หนึ่งตัวหลัง `run_command` เป็น `ACTIVE` ซึ่งอยู่คนละ process group กับ CLI และยังปรากฏหลังส่ง SIGKILL ไปยัง group ของ CLI หนึ่งวินาที; permission ชั่วคราวถูกลบและตรวจซ้ำแล้ว ผลนี้แสดงว่า process group kill ไม่เพียงพอสำหรับยืนยัน cancellation และยังห้ามปล่อยคิวจากหลักฐานนี้
- ตรวจ parent ก่อน cancel ในการทดลอง `sleep 37` ซ้ำ: sleep เป็น child โดยตรงของ agy CLI แต่มี process group ต่างกัน และยังปรากฏหลังฆ่า group ของ CLI; การตาม parent PID อย่างเดียวจึงยังไม่เป็นหลักประกันเมื่อ process สามารถแยก group หรือถูก reparent ได้ Permission ชั่วคราวถูกลบแล้ว
- ทดลอง `sleep 37` อีกครั้งโดยส่ง SIGINT แทน SIGKILL หลังพบ sleep process จริง: CLI หยุดภายใน 8 วินาทีและไม่พบ sleep PID เดิมในการตรวจหลังจากนั้นหนึ่งวินาที; permission ชั่วคราวถูกนำออกแล้ว นี่เป็นหลักฐานของ graceful cancellation สำหรับคำสั่งนี้หนึ่งครั้งเท่านั้น ยังไม่ยืนยัน subprocess ชนิดอื่น, กรณี CLI ไม่ตอบสนอง หรือการยืนยัน process identity จึงยังไม่ใช้ปลดคิวอัตโนมัติ
- [Headless mode](https://antigravity.google/docs/cli/headless/) ระบุว่า stream input ยังไม่รองรับ `control_request`/`control_response` และการปิด stdin รอ turn ปัจจุบันจบ จึงยังไม่พบ protocol cancellation ที่ยืนยันการหยุด child จากเอกสารนี้
- ทดสอบ SIGINT ระหว่าง `sleep 37` ซ้ำและตรวจ stream: CLI ส่ง terminal `result.status` เป็น `ERROR` และไม่พบ sleep PID เดิมหลังหยุดหนึ่งวินาที; จึงห้ามตีความ `ERROR` เพียงอย่างเดียวว่าเป็น cancellation สำเร็จ Permission ชั่วคราวถูกลบแล้ว
- วิเคราะห์เพิ่มเติมด้วย `agy` จากข้อมูลสังเคราะห์ใน workspace ชั่วคราว โดยไม่ส่ง source code: แนวทางที่เสนอรวมการติดตาม process tree, launchd และ filesystem isolation ยังไม่ได้รับการพิสูจน์ว่าเก็บ descendant ได้ครบหรือหยุดการแก้ไฟล์จาก daemon ภายนอกได้; การตรวจ `lsof` เพียงช่วงเดียวไม่ตัดความเป็นไปได้ที่จะเปิดไฟล์ภายหลัง และการ force unmount อาจทำให้ข้อมูลเสีย จึงยังไม่ใช้เป็นหลักฐานปลดคิว งานวิจัยของ Apple อธิบายการทำงานของ [launchd](https://developer.apple.com/library/archive/documentation/MacOSX/Conceptual/BPSystemStartup/Chapters/Lifecycle.html) แต่ไม่ได้ยืนยัน contract ว่าการหยุด CLI จะหยุด descendants ทั้งหมด
- Adapter ตรวจ canonical `cwd`, model `gemini-3.8-flash-medium` และ permission mode จาก `init` ก่อนส่ง prompt; หากไม่ตรงหรืออ่าน path ไม่ได้จะปฏิเสธ ทดสอบทั้ง runtime จำลองและ CLI จริงด้วย prompt สังเคราะห์แล้ว การตรวจนี้ยังไม่ยืนยัน sandbox หรือการหยุด descendants
- ทดลองทางเลือก Docker บนเครื่อง: Engine เป็น Linux/arm64; container ชั่วคราวที่ไม่มี network หรือ project mount รัน `sleep 60` ใน session แยก และ `docker kill` ทำให้ container หยุด (exit 137) จากนั้นลบ container แล้ว การทดลองนี้ยังไม่ตรวจ `agy` จริงหรือ process ที่ส่งงานให้ daemon ภายนอก
- [Docker documentation](https://docs.docker.com/reference/cli/docker/container/run/#pid-settings---pid) ระบุว่า container ใช้ PID namespace แยกเป็นค่าเริ่มต้น และ [Linux pid_namespaces(7)](https://man7.org/linux/man-pages/man7/pid_namespaces.7.html) ระบุว่าเมื่อ init ของ namespace จบ kernel ส่ง SIGKILL ให้ process อื่นใน namespace; จึงเป็นแนวทาง containment ที่ควรพิสูจน์ต่อ โดยต้องไม่ใช้ host PID namespace หรือ mount Docker socket และต้องจัดการสถานะเมื่อ Docker daemon ติดต่อไม่ได้
- การรัน `agy` ภายใน Linux container ต้องพิสูจน์ Linux/arm64 build, การ mount project และ authentication แยกก่อน: [เอกสาร authentication](https://antigravity.google/docs/cli/install/) ระบุว่า CLI ใช้ native keyring ของระบบ หรือ Gemini API key/ADC ตาม configuration; ยังไม่ได้ยืนยันว่า session ใน macOS ใช้ภายใน container ได้ ห้ามคัดลอก credential หรือ mount keyring โดยอัตโนมัติ
- ตรวจ installer ทางการและดาวน์โหลด Linux/arm64 musl build จาก URL ใน manifest โดยตรวจ SHA-512 แล้ว; binary `agy --help` เริ่มได้ใน `postgres:17-alpine` container แบบไม่มี network, project mount หรือ credential
- ทดลอง headless prompt ใน container โดยใช้ HOME ชั่วคราวและไม่มี network/credential: CLI แสดง OAuth authorization flow และรอ input แทนการจบอัตโนมัติในช่วงที่สังเกต จึงต้องออกแบบ startup timeout และสถานะ authentication แยกก่อนเปิดใช้ หยุดและลบ container ทดสอบแล้ว ไม่ได้ใช้หรือย้าย credential ของผู้ใช้

## ข้อกำหนดก่อนเชื่อม Docker execution กับคิว

- ก่อนสร้าง container ต้องบันทึก identity ที่ไม่ซ้ำและสัมพันธ์กับ task แบบ durable เพื่อให้ recovery ค้นหาได้แม้ Backend หยุดระหว่างสร้างหรือเริ่ม container; ห้ามเริ่ม task ถัดไปเมื่อยังระบุ execution เดิมไม่ได้
- ระบุ Docker daemon ที่ใช้งานร่วมกับ container identity และตรวจ ownership/labels ก่อนสั่งหยุดหรือลบ ห้ามสั่งจากชื่อหรือ PID ที่อาจถูกนำกลับมาใช้เพียงอย่างเดียว; หาก daemon เปลี่ยน ติดต่อไม่ได้ หรือผลตรวจไม่ชัดเจน ให้คง project blocked
- การยกเลิกต้องส่งคำขอหยุดและรอหลักฐานจาก Docker ว่า container ที่ระบุหยุดแล้ว ก่อนยืนยัน cancellation หรือปลดคิว; timeout หรือการตรวจไม่สำเร็จต้องถือเป็นสถานะไม่แน่นอน ไม่ถือว่า kill สำเร็จจาก exit code ของ CLI เพียงอย่างเดียว
- Recovery ปัจจุบันใช้ host/boot identity สำหรับ Codex บน host เท่านั้น; ห้ามนำเงื่อนไข boot session ที่เปลี่ยนมาเป็นหลักฐานโดยตรงว่า container execution ปลอดภัย ต้องตรวจ Docker daemon และ container ตาม identity ที่บันทึกไว้ก่อน
- Container ต้องมี PID namespace ของตัวเอง ไม่มี Docker socket หรือสิทธิ์ privileged และต้องแยก HOME/credentials ของ provider จาก project mount; ต้องตรวจการทำงานจริงและขอบเขต side effect รวมถึงการสื่อสารกับบริการภายนอกก่อนอ้างว่า subprocess ทั้งหมดอยู่ภายใต้การควบคุม
- การเพิ่ม authentication ต้องเป็นขั้นตอนที่ผู้ใช้ตั้งค่าเองอย่างชัดเจน ไม่ส่ง credential เข้า task prompt, event, database หรือ logs; ยังไม่ได้ตัดสินวิธีแชร์ authentication ระหว่าง macOS กับ Linux container
- เตรียม [Dockerfile ทดลอง](../../../backend/antigravity.Dockerfile) สำหรับ `agy` 1.4.9 โดยตรึง URL และ SHA-512 แยก arm64/amd64; build และรัน `--help` บน Linux/arm64 สำเร็จใน container ที่ไม่มี network และใช้ `--read-only` พร้อมตรวจว่ารันเป็น UID 1000 ผลนี้ยังไม่ยืนยัน amd64, project mount, authentication หรือการใช้งานจริง และ Dockerfile ยังไม่ได้เชื่อมกับ Backend
- ทดสอบ bind mount จาก directory ชั่วคราวของ macOS ที่ใช้ permission ปกติ: container image ทดลองรันเป็น UID 1000 โดยไม่มี network และ `--read-only` สำหรับ root filesystem สามารถอ่านไฟล์ fixture และสร้างไฟล์ใน mount ได้ ผลนี้ยืนยันเฉพาะ Docker Desktop/environment ปัจจุบัน ไม่รับประกัน permission ของ project ทุกตัวหรือการใช้งาน `agy` กับ credential
- Build image สำหรับ linux/amd64 และตรวจ SHA-512 ผ่านแล้ว; `--help` ผ่านภายใต้ emulation บน Docker Desktop เครื่องนี้เมื่อจัด tmpfs ให้ `/tmp` การรันแบบ read-only โดยไม่มี tmpfs ทำให้ emulator สร้าง temporary file ไม่ได้ จึงต้องกำหนดพื้นที่ชั่วคราวเมื่อออกแบบ runtime; ยังไม่ได้ทดสอบบนเครื่อง Intel จริง
- เพิ่ม `StopContainer` สำหรับตรวจ Docker daemon ID, full container ID, execution ownership label, PID namespace, restart policy และ privileged mode ก่อนสั่งหยุด; หลังหยุดตรวจ daemon และ container ซ้ำ หากตรวจไม่ได้หรือยัง running จะคืนสถานะไม่ยืนยัน ฟังก์ชันนี้ยังไม่ถูกเรียกจาก worker และยังไม่มีการบันทึก identity ลง database จึงยังไม่เปิด provider
- ทดสอบ ownership mismatch และ kill ที่ตรวจยืนยันไม่ได้ด้วย Docker จำลอง; opt-in test `DOCKER_CONTAINMENT_TEST=1 go test ./internal/antigravity -run TestDockerStopContainer` สร้าง container ชั่วคราวแบบไม่มี network/mount และตรวจการหยุดซ้ำได้ ผลทดสอบยังไม่ครอบคลุม daemon เปลี่ยนระหว่าง operation หรือ side effects นอก container
- Recovery บันทึก provider ของ execution ที่ทำให้ project blocked แล้ว และใช้หลักฐาน boot session ปลดคิวอัตโนมัติเฉพาะ Codex; provider อื่นยังคง blocked แม้ boot เปลี่ยน จนกว่าจะมี recovery ที่ยืนยัน runtime นั้นได้ Migration ตั้ง provider ของ block เดิมเป็น Codex เพราะก่อนหน้านี้เปิดใช้งานได้เฉพาะ Codex
- Database มี `container_executions` สำหรับบันทึก owner token และ daemon identity ก่อนสร้าง container และผูก full container ID ได้ครั้งเดียวขณะ Antigravity task กำลังทำงาน; test ตรวจ provider, ownership, การเขียนซ้ำ และการคง identity หลัง task ล้มเหลวแล้ว ส่วนการสร้าง container, การค้นหาด้วย label หลัง crash และ recovery ยังไม่ได้เชื่อมกับ worker
- เพิ่มการค้นหา container ด้วย owner token บน daemon เดิมสำหรับกรณีสร้าง container แล้วแต่ยังไม่บันทึก ID: ต้องพบเพียงหนึ่งตัวและตรวจ identity/ownership/isolation ได้ครบ มิฉะนั้นคืนสถานะไม่ยืนยัน; การตรวจสถานะหลังหยุดยังปฏิเสธข้อมูลที่ขาด, PID ไม่สอดคล้อง, restarting หรือ dead ทดสอบด้วย Docker จำลองและ container ชั่วคราวจริงแล้ว ขณะบันทึกผลทดสอบนี้ยังไม่ได้เชื่อมกับ startup recovery
- Project ที่ถูก block จะบันทึก task ID ที่ทำให้ block; เพิ่ม store operation สำหรับค้น identity ของ Antigravity ที่ blocked และปลดเฉพาะ task/owner/daemon/container ที่ตรงกัน โดย caller ต้องตรวจว่า container หยุดแล้วก่อนเรียก การปลดบันทึก project event แบบ atomic และ frontend โหลด project state ใหม่ ขณะบันทึกผลทดสอบนี้ยังไม่ได้ถูกเรียกจาก startup recovery
- Startup recovery เรียกตรวจ blocked Antigravity containers หลังทำเครื่องหมาย task ที่ค้างเป็น failed: หากมี container ID ใช้ identity ที่บันทึก หากไม่มีให้ค้นด้วย owner token; ตรวจและหยุด container ก่อนปลด block แบบ atomic เมื่อ Docker ไม่พร้อม ข้อมูลไม่ตรง หรือสถานะไม่ยืนยัน จะคง block ไว้ ทดสอบด้วย PostgreSQL, runtime จำลอง และ Docker container ชั่วคราวจริงแล้ว; container ที่อยู่ `created`, `restarting` หรือ `dead` ไม่ถือว่าหยุดปลอดภัย
- เพิ่ม `CreateContainer` รุ่นทดลองสำหรับสร้าง container ด้วย deterministic owner, image digest, non-root, read-only root filesystem, ลด capabilities, no-new-privileges, tmpfs และ project bind mount; ตรวจ configuration ผ่าน inspect ก่อนคืน identity และทดสอบกับ Docker จริงโดยใช้ project ชั่วคราวที่มี comma ใน path แล้ว ปัจจุบันบังคับ `--network none` และยังไม่เรียกจาก worker จึงไม่สามารถติดต่อ model provider ได้
- Auto-review ปฏิเสธการยอมรับ Docker `bridge` network เพราะเป็นการขยาย network access; ต้องได้รับอนุญาตและออกแบบขอบเขต network/ข้อมูลก่อนเปลี่ยนไปใช้ network ที่ติดต่อ provider ได้
- เพิ่มขั้นเตรียม container: จอง owner token/daemon ใน PostgreSQL ก่อนเรียก Docker และบันทึก container ID หลังตรวจ configuration; เมื่อสร้างไม่ยืนยันได้ identity ที่จองไว้ยังอยู่เพื่อ recovery ผู้เรียกต้อง block project เมื่อเกิดความไม่แน่นอน ทดสอบลำดับกับ runtime จำลองและ PostgreSQL รวมทั้งสร้าง container offline จริงใน project ชั่วคราวแล้ว ขั้นนี้ยังไม่เชื่อมกับ worker หรือส่ง prompt
- เพิ่ม `RunContainer` รุ่นทดลอง: ตรวจ container ที่สร้างไว้แล้ว, รับ init และตรวจ cwd/model/permission ก่อนส่ง prompt ผ่าน stdin, จำกัด output และตรวจ Docker หลังจบหรือยกเลิก; คืน `Stopped=false` หากยืนยันการหยุดไม่ได้ ทดสอบใน Docker แบบ `--network none` ด้วย runtime จำลองทั้ง success, model ไม่ตรง และ cancel ขณะ subprocess ทำงาน ยังไม่ได้เชื่อม worker หรือใช้ `agy` จริงพร้อม credential
- เพิ่ม executor ทดลองที่ต่อการจอง identity, สร้าง container, handshake, รัน และยืนยันการหยุดเข้ากับ worker พร้อม redaction ค่า `GEMINI_API_KEY` ที่รู้จัก ทดสอบ end-to-end ด้วย PostgreSQL และ runtime จำลองใน Docker แบบ offline; API และ scheduler ยังไม่เปิด Antigravity และยังไม่ได้ทดสอบบัญชีจริง
- Scheduler รองรับการลงทะเบียน executor Codex และ Antigravity แยกกัน โดยเลือกเฉพาะ provider ที่ลงทะเบียน และยังคง FIFO ข้าม provider ต่อ project; หาก provider แรกไม่พร้อม งานถัดไปของ project นั้นไม่ถูกแซง แต่ project อื่นยังรันได้ ทดสอบด้วย PostgreSQL/runtimes จำลองและ Docker offline แล้ว Production ยังคงลงทะเบียนเฉพาะ Codex และ API ยังไม่อนุญาตสร้าง Antigravity task
- ชั้น store และ scheduler ทดสอบ workflow ลำดับ Codex → Antigravity → Codex ด้วย runtime จำลองแล้ว โดยส่งผลลัพธ์ของแต่ละขั้นต่อกัน API ยังคืน 409 หาก workflow ระบุ Antigravity จนกว่าการเชื่อมต่อจริงจะพร้อม

- Task และ workflow API ตรวจ availability ของ provider ที่ร้องขอแต่ละตัว; ไม่บังคับให้ Codex พร้อมสำหรับ workflow ที่ใช้ Antigravity อย่างเดียว และไม่ fallback ไป provider อื่น
- `GET /api/providers` รายงาน Antigravity cancellation ตาม availability และยังรายงาน interactive approval ว่าไม่รองรับ ค่าเริ่มต้นของ production เป็น unavailable; main ยังคงลงทะเบียน executor เฉพาะ Codex
- ทดสอบ HTTP → worker → PostgreSQL สำหรับ Codex → Codex, Codex → Antigravity และ Antigravity → Antigravity ด้วย runtime จำลอง รวมการส่งต่อผลลัพธ์และ redaction; กรณีสุดท้ายตั้ง Codex unavailable เพื่อยืนยันว่าแต่ละ provider ตรวจแยกกัน
